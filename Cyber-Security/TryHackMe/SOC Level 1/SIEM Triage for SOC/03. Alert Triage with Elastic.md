## Uncovering Account Activity

I discovered some red flags in the web log previously. But suspicious network traffic is only part of the story. It's now time to pivot into host based evidence to uncover more of the story and determine if the attacker has moved further.

**ALERT #3**

<img width="481" height="205" alt="image" src="https://github.com/user-attachments/assets/84457523-1eb0-4991-bdf0-dca6507ae46d" />

A new alert has come in and it shows that an Administrator account has accessed the server outside of business hours.
My first move here is to confirm the logon - when it happened, how it happened and from where?
I'll start my search in Elastic with the event code 4624 against the hostname and Administrator account.

`@timestamp >= "2025-07-20T05:11:22" and winlog.event_id:4624 and host.name:winserv2019.some.corp and winlog.event_data.TargetUserName:Administrator`

And just like before. I will add the following fields so the data is displayed in a more structured and legible way for this investigation.

    winlog.event_id
    host.name
    winlog.event_data.TargetUserName
    winlog.logon.type
    winlog.event_data.IpAddress

<img width="1002" height="272" alt="image" src="https://github.com/user-attachments/assets/3348e0d2-ce26-490f-b909-eb3f1435bf6c" />

I can see now that the suspicious IP address from the previous alerts (203.0.113.55) successfully logged onto the Administrator account on host winserv2019.some.corp

I can also correlate Sysmon logs to validate the Administrator authentication and investigate what happened after. So I will adjust my search query and selected fields to look into Sysmon Event ID: 1 (Process Creation)

`@timestamp >= "2025-07-20T05:11:22" and winlog.event_id:1 and user.name: "Administrator"`

    user.name
    process.parent.name
    process.command_line

<img width="1273" height="934" alt="image" src="https://github.com/user-attachments/assets/ebd61078-6006-46b7-b405-5142b271d283" />

From this I can verify the Administrator logon initiated a process chain that aligns with Windows session initialization. The 2 queries have helped me confirm the logon occurred but the evidence I have so far isn't enough to validate any malicious behavior. Perhaps the Administrator started work earlier today. So i will investigate the next alert to see what the Administrator account was up to.

## Exposing Command Execution

**Alert #5**

<img width="481" height="204" alt="image" src="https://github.com/user-attachments/assets/160c56fe-a8cd-4a7a-9f52-d1b42cd9ed0f" />

This next alert flagged suspicious command-line execution from the same Administrator account. Perhaps the attacker is escalating their actions here.

I will investigate the following as a L1 analyst

    1. Scope the alert: Identify the child processes launched by cmd.exe
    2. Confirm the origin: Find out who launched cmd.exe and why
    3. Check for privilege changes: Look for commands like net used to add users to groups
    4. Correlate across log sources: Use Sysmon and Windows Security logs to confirm the malicious behavior


I need to craft a query that searches on or after the time mentioned in the alert and include the parent process of cmd.exe - this will help me see what commands have been executed.

`@timestamp >= "2025-07-20T05:13:15.000" and process.parent.name:cmd.exe and user.name:Administrator`

and a simple table to view the data

    process.command_line
    process.name
    process.parent.name

<img width="1004" height="392" alt="image" src="https://github.com/user-attachments/assets/58a0e007-78d1-4f24-8475-3016e3f7fa14" />

I now know the new account has been added to 3 groups. I'll now correlate this with the Windows Security Event ID: 4732 (Security Group Management)

`@timestamp >= "2025-07-20T05:13:15" and (winlog.event_id:4732 or process.parent.name:cmd.exe)`

<img width="994" height="924" alt="image" src="https://github.com/user-attachments/assets/8f5502ed-c7eb-447b-b216-764d941e4453" />

I can verify that the Administrator has used CMD to create a user and modify security groups. I could now use Sysmon logs to determine if the attack ends here. But let me look into some Powershell logs.

I'll refine the search to be:

`@timestamp >= "2025-07-20T05:13:15.000" and event.module:powershell and event.code:4104`

and change the table field to have `powershell.file.script_block_text` so I can see the commands run in plaintext
and lastly, I'll sort the data to be Old-New so I can see the first commands run.

<img width="1276" height="910" alt="image" src="https://github.com/user-attachments/assets/c20b47a8-d980-4035-84e0-57a72fec1cb5" />

The search results show that the commands **whoami** and **whoami /priv** were run. These are classic discovery commands used by attackers to see which account they are running under and what privileges they have.

## No Alert Created!

At this point I have been able to build a timeline of events around this activity
1. A proxyLogon exploitation of the web app
2. A backdoor RDP login as Administrator
3. Backdoor user setup and management through CMD
4. Further evidence through Powershell

But not all malicious activity is captured by the alerts, so it's important that I remain vigilant and look deeper into the logs to determine if any other plays have been made.

If I look back to the correlation search of Event ID: 4732 I can see an unusual `.rar` file execution made by the new user svc_backup

<img width="994" height="924" alt="image" src="https://github.com/user-attachments/assets/04bc9d3b-2479-465c-bc80-ff6357cc748b" />

No alert may have been created for this as RAR may be a legitimate piece of software used by the client.

<img width="988" height="1093" alt="image" src="https://github.com/user-attachments/assets/88dc6802-c619-4702-8d3f-c6df7f517f61" />

I can see the attacker has created an archive in the Temp folder named `finance_it_archive.rar` which could indicate an attempt to establish staging or a means of collection, leading into data exfiltration. In either case, I have identified key indicators of malicious activity through this investigation. As a L1 analyst I would ensure these alerts are classified as true positives and escalated to L2 and any other appropriate personnel.
